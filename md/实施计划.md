# 企业微信群发系统 — 实施计划

## 一、项目概述

### 1.1 系统定位

面向企业微信外部客户群的 **客服响应监控 + 超时预警 + 定向群发** 三合一系统，采用「主控端 + 多执行端」分布式架构。

### 1.2 核心能力

| 能力 | 描述 |
|---|---|
| 📡 实时监控 | 持续轮询企微客户端聊天列表，检测客户发言，追踪当日活跃群 |
| 🚨 超时预警 | 客户发言 5 分钟内无员工回复 → 全端弹窗 + 声音 + Web 高亮 |
| 📨 定向群发 | 仅在当日活跃群（约 20-50 个）定时发送模板化消息 |
| 👥 任务分配 | 主控按分配策略将群发任务分发给在线执行端 |
| 🔄 离线接管 | 执行端离线后自动将其负责的群转交给在线同事 |

### 1.3 规模与环境

| 维度 | 参数 |
|---|---|
| 目标群数量 | 200-500 个企业微信客户群 |
| 日活跃群 | 约 20-50 个 |
| 执行端数量 | ~5 个同事 |
| 网络环境 | 跨网段，不在同一局域网 |
| 预算 | 零预算，完全自研 |

### 2.2 通信机制

**主方案：内置 WebSocket 中继**
- 项目自带 `relay.py`（约 100 行），部署到 Render / Fly.io 免费层
- 所有端启动后自动连接中继，通过中继透明转发消息
- 中继无状态、无业务逻辑，只做消息路由

**增强：局域网自动直连**
- 启动时通过 mDNS / UDP 广播探测主控
- 同局域网内自动直连，零延迟、不消耗中继带宽
- 探测不到才走中继

**连接架构**：
```
执行端启动
  → 尝试局域网发现 (mDNS/UDP广播)
    ├─ 找到主控 → 直连 ws://192.168.x.x:8080 ✅
    └─ 未找到   → 连接中继 ws://relay.example.com ✅
```

## 三、核心模块设计

### 3.1 消息监控引擎

**监控流程**（运行于每个执行端 + 主控兜底）：

```
每 30 秒轮询:
  1. 通过 uiautomation 定位企微聊天列表控件
  2. 遍历可见列表项，提取：群名 + 最后消息预览
  3. 从消息预览中解析「发送者名称」
  4. 正则匹配判断客户/员工:
     - 匹配员工规则 → 员工发言 → 更新该群「最后回复时间」
     - 不匹配      → 客户发言 → 标记活跃群 + 记录发言时间
  5. 上报主控: {group_name, is_customer, timestamp}
```

**客户/员工识别规则**：
- 配置员工名称正则，如 `^.*@公司名$`
- 支持白名单补充

**降级方案**：
- 当 UIA 无法识别元素时 → 截图聊天列表区域 → OCR 识别（paddleocr）
- OCR 提取群名和发送者名称

### 3.2 超时预警引擎

**检测逻辑**（主控端运行）：

```
每 10 秒遍历所有活跃群:
  IF 客户最后发言时间存在
     AND (员工最后回复时间 IS NULL OR 员工最后回复时间 < 客户最后发言时间)
     AND 当前时间 - 客户最后发言时间 > 300 秒
     AND 该群尚未触发预警 OR 上次预警已被确认后又新超时
  THEN
     → 广播预警消息至所有在线执行端
     → 主控 Web 界面高亮该群
```

**预警去重**：
- 首次超时 → 弹窗 + 声音 + Web 高亮
- 持续超时 → 仅保持 Web 高亮，不重复弹窗
- 员工回复 → 自动解除预警
- 确认后又有新超时 → 重新触发

**预警升级链**：
- 5 分钟 → 全端弹窗提醒
- 10 分钟 → 主控 Web 界面升级为严重标记
- 15 分钟 → 记录为「严重超时事件」

### 3.3 RPA 发送引擎

**发送流程**（执行端）：

```
收到发送任务:
  for each 群 in 任务列表:
    1. 通过 uiautomation 在企微搜索框搜索群名
    2. 定位搜索结果 → 双击进入群聊
    3. 定位消息输入框 → 粘贴渲染后的消息
    4. 按 Enter 发送
    5. 检测发送状态（通过 UI 反馈判断成功/失败）
    6. 随机延迟 2-5 秒（防止触发风控）
    7. 上报结果给主控
```

**消息模板**（Jinja2）：
```
【{{通用标题}}】
{{通用内容}}
---
{{该群自定义备注}}
```

### 3.4 任务调度引擎

**定时群发**：
- 通过 APScheduler 配置 Cron 表达式（如 `0 9 * * *` 每天 9:00）
- 触发后：主控读取当日活跃群 → 按分配关系拆分为各执行端任务 → WS 下发

**手动群发**：
- 主控 Web 界面点击「立即发送」→ 同上流程

**断点续传**：
- 每发送完一个群立刻写进度 JSON
- 中断后重启从断点继续，不重复发送

### 3.5 离线接管机制

```
心跳周期: 执行端每 10s → 主控

主控检测:
  超过 30s 未收到心跳 → 标记执行端「离线」
  → 读取该执行端负责的群列表
  → 按以下优先级重分配:
     1. 同组备份（如果配置了）
     2. 当前负载最轻的在线执行端
  → 下发「新增监控群」指令给目标执行端
  → 更新分配表

执行端恢复上线:
  → 主控可选择:
     A. 归还原群（恢复原分配）
     B. 保持新分配（原执行端加入空闲池）
```

## 五、技术栈

| 层 | 技术 | 用途 |
|---|---|---|
| 通信 | WebSocket (websockets / FastAPI) | 主控-执行端双向实时通信 |

| 模板 | Jinja2 | 消息模板渲染 |
| 调度 | APScheduler | Cron 定时 |
| 桌面通知 | `win10toast` / `plyer` | Windows 原生通知 |
| 音频 | `playsound` | 预警 wav 播放 |
| 持久化 | YAML + JSON | 配置与状态存储 |
| 打包 | PyInstaller | 单文件 exe 分发 |

## 七、关键风险与应对

| 风险 | 等级 | 应对 |
|---|---|---|
| UIA 无法读取企微聊天列表 | 🔴 高 | 提前验证；OCR 降级方案已就绪 |

## 八、运行部署

### 8.1 中继部署

```
# relay.py 部署到 Render 免费层:
#   - 选择 Python + Web Service
#   - 启动命令: python relay.py
#   - 环境变量: PORT=8080
```

### 8.2 主控端启动

```
python main.py --mode master --port 8080
```

### 8.3 执行端启动

```
python main.py --mode worker --relay ws://your-relay.onrender.com --account 张三
```

### 8.4 配置示例 (config.yaml)

```yaml
relay_url: "ws://your-relay.onrender.com"
master_port: 8080

# 员工名匹配规则
staff_patterns:
  - regex: ".*@公司名$"
  - whitelist: ["张三", "李四"]

# 预警配置
alert:
  timeout_seconds: 300  # 5 分钟
  heartbeat_interval: 10
  offline_threshold: 30
  retry_count: 3

# 群发配置
send:
  send_delay_min: 2   # 群间最小延迟(秒)
  send_delay_max: 5   # 群间最大延迟(秒)
  schedule_cron: "0 9 * * *"  # 每天 9:00
```

## 九、验收标准

| 场景 | 预期结果 |
|---|---|
| 客户在群内发言 | 30 秒内被监控引擎检测到，标记为活跃群 |
| 客户发言后 5 分钟无回复 | 所有在线端弹窗 + 声音 + Web 高亮 |
| 员工回复后 | 预警自动解除 |
| 定时群发触发 | 仅对当日活跃群发送，20-50 群约 2-5 分钟完成 |
| 某执行端关机 | 30 秒后主控检测离线，自动将其群分配给在线端 |
| 执行端重启 | 心跳恢复，状态同步，断点续发 |
| 中继不可用 | 同局域网端自动直连，跨网络端降级独立运行 |
